# State Transition Rules v1.0

## 1. Scope

เอกสารนี้กำหนดเงื่อนไขการเปลี่ยนสถานะของ `ApprovalCase` ในกระบวนงานคำขอ → วิเคราะห์ → ตรวจฐานอำนาจ → เลือกขั้นอนุมัติ → จัดทำร่าง → ตรวจคุณภาพ → ตรวจทานโดยมนุษย์ โดยสถานะเป็นตัวควบคุมสิทธิ์ ไม่ใช่เพียงป้ายแสดงผลบนหน้าจอ

## 2. State machine

```text
RECEIVED
  -> FACT_REVIEW
  -> INTENT_STAGE_ANALYSIS
  -> CLASSIFICATION_PENDING
  -> AUTHORITY_CHECK
  -> APPROVAL_STAGE_SELECTION
  -> READINESS_ASSESSMENT
  -> DRAFT_ALLOWED
  -> QUALITY_GATE
  -> HUMAN_REVIEW
  -> READY_FOR_SUBMISSION
```

ทุกสถานะสามารถย้อนกลับไป `FACT_REVIEW` หรือ `AUTHORITY_CHECK` ได้เมื่อพบข้อเท็จจริงใหม่ หลักฐานใหม่ หรือความขัดแย้งของกฎ

## 3. Transition contract

| From | To | เงื่อนไขขั้นต่ำ | ห้ามเปลี่ยนเมื่อ |
|---|---|---|---|
| RECEIVED | FACT_REVIEW | มี requestText และ caseId | ไม่มีแหล่งที่มาของคำขอ |
| FACT_REVIEW | INTENT_STAGE_ANALYSIS | แยก facts, assumptions และ missing information แล้ว | ข้อมูลสำคัญถูกตีความเป็นข้อเท็จจริง |
| INTENT_STAGE_ANALYSIS | CLASSIFICATION_PENDING | ระบุวัตถุประสงค์และประเภทการดำเนินการเบื้องต้น | ไม่ทราบวัตถุประสงค์จนไม่สามารถวิเคราะห์ต่อได้ |
| CLASSIFICATION_PENDING | AUTHORITY_CHECK | มีผลจำแนกรายการหรือระบุเหตุผลว่าต้องรอหลักฐาน | มีรายการ conflicting หรือข้อมูลจำแนกสำคัญหายไปโดยไม่เปิด lock |
| AUTHORITY_CHECK | APPROVAL_STAGE_SELECTION | ตรวจผู้มีอำนาจ ช่วงเวลา ฉบับใช้บังคับ และแหล่งอ้างอิงแล้ว | มี conflict, version ไม่ชัด หรือยังไม่มีหลักฐานปฐมภูมิที่จำเป็น |
| APPROVAL_STAGE_SELECTION | READINESS_ASSESSMENT | เลือกขั้นเอกสารโดยอิงข้อเท็จจริงและอำนาจหน้าที่ | เลือกขั้นจากคำสั่งผู้ใช้เพียงอย่างเดียวโดยข้ามขั้นก่อนหน้า |
| READINESS_ASSESSMENT | DRAFT_ALLOWED | เงื่อนไขและเอกสารประกอบของขั้นนั้นครบ หรือระบุ non-blocking gap อย่างชัดเจน | มี blocking missing information, decision lock หรือ risk critical ที่ยังไม่จัดการ |
| DRAFT_ALLOWED | QUALITY_GATE | สร้างร่างจากข้อมูลใน case เท่านั้น | มีการเติมข้อมูลที่ไม่ได้มาจากหลักฐาน |
| QUALITY_GATE | HUMAN_REVIEW | ทุก quality checks ที่เป็น mandatory ผ่าน | มี check fail หรือ pending ในรายการบังคับ |
| HUMAN_REVIEW | READY_FOR_SUBMISSION | ผู้ตรวจทานยืนยันและมี audit trail | ไม่มีผู้ตรวจทาน หรือมีการแก้สาระสำคัญหลังตรวจทาน |

## 4. Mandatory gates

### 4.1 Fact Gate

ตรวจว่า:

- ข้อเท็จจริงทุกข้อมี source และสถานะความเชื่อมั่น
- ข้อสันนิษฐานถูกแสดงแยกต่างหาก
- ข้อมูลสำคัญที่ขาดถูกระบุพร้อมผลกระทบ
- ไม่ใช้ keyword เป็นเหตุผลเดียวในการจำแนกประเภท

### 4.2 Applicable Authority Gate

ตรวจอย่างน้อย:

- AUTHORITY: หน่วยงาน/ผู้มีอำนาจที่เกี่ยวข้อง
- VERSION: ฉบับและการแก้ไข
- TIME: วันที่เกิดเหตุและช่วงเวลาที่กฎมีผล
- FACT_MATCH: ข้อเท็จจริงตรงกับเงื่อนไขของกฎหรือไม่
- LATER_CHANGE: มีหนังสือหรือกฎภายหลังเปลี่ยนแปลงหรือไม่
- CONFLICT_TRANSITION: มีบทเฉพาะกาลหรือแหล่งอ้างอิงขัดกันหรือไม่

ระบบต้องเริ่มค้นหาได้แม้ข้อมูลยังไม่พอสำหรับการตัดสิน แต่ต้องไม่ปลดล็อกการตัดสินจนกว่าจะตรวจเงื่อนไขที่จำเป็นครบ

### 4.3 Procurement Gate

ตรวจความสอดคล้องของ:

- ประเภทพัสดุและลักษณะการได้มา
- การรวมรายการและความเสี่ยงแบ่งซื้อแบ่งจ้าง
- วงเงิน แหล่งเงิน และปีงบประมาณ
- วิธีจัดซื้อจัดจ้างและขั้นตอน e-GP ที่ใช้ในช่วงเวลานั้น
- TOR/คุณลักษณะเฉพาะที่ไม่ล็อกยี่ห้อโดยไม่มีเหตุผลตามกฎหมาย
- เอกสารอนุมัติที่ต้องมีมาก่อนการดำเนินการขั้นถัดไป

ต้องตรวจหนังสือเวียนปัจจุบันจากแหล่งทางการ เช่น แนวทาง ว714 ลงวันที่ 16 กันยายน 2569 ก่อนนำกฎ e-GP ไปใช้ และห้ามถือว่าหนังสือฉบับเก่ายังคงใช้โดยอัตโนมัติ

### 4.4 Draft Gate

ร่างเอกสารต้อง:

- ระบุชัดว่าเป็น “ร่างเพื่อการตรวจทาน” จนกว่าจะผ่าน Human Review
- ไม่ใส่เลขที่หนังสือ วันที่ คำสั่งอนุมัติ หรือชื่อผู้ลงนามที่ไม่มีหลักฐาน
- แยกช่องที่ต้องกรอก/ตรวจสอบด้วยมนุษย์
- เชื่อมข้อเสนอแต่ละข้อกับ fact หรือ evidence reference

## 5. Decision Lock policy

เปิด lock ทันทีเมื่อ:

- พบเงื่อนไขทางกฎหมายที่ยังตัดสินไม่ได้
- มีหลักฐานขัดแย้ง
- ไม่ยืนยันอำนาจหรือฉบับกฎหมายที่ใช้
- มีข้อมูลสำคัญที่ส่งผลต่อวงเงิน วิธีจัดซื้อ ประเภทพัสดุ หรือขั้นอนุมัติ
- พบความเสี่ยงสูง/วิกฤตที่ยังไม่มีมาตรการลดความเสี่ยง
- ผู้ใช้ขอข้ามขั้นอนุมัติหรือขอให้ระบบรับรองความถูกต้องโดยไม่มีหลักฐาน

เมื่อ lock เปิด ระบบทำได้เพียง:

1. สรุปข้อเท็จจริงที่ยืนยันได้
2. ระบุประเด็นที่ยังตัดสินไม่ได้
3. สร้างรายการหลักฐานที่ต้องค้นหรือขอเพิ่ม
4. เสนอทางเลือกเชิงกระบวนงานโดยไม่ออกคำสั่งสุดท้าย

## 6. Re-entry and invalidation

- หากมีเอกสารใหม่ที่เปลี่ยนสาระสำคัญ ให้ย้อนกลับอย่างน้อย `FACT_REVIEW`
- หากมีการเปลี่ยนกฎหมาย หนังสือสั่งการ หรือวันที่มีผล ให้ย้อนกลับ `AUTHORITY_CHECK`
- หากเปลี่ยนวงเงิน แหล่งเงิน รายการ หรือวิธีจัดซื้อ ให้ย้อนกลับ `APPROVAL_STAGE_SELECTION` และประเมิน Quality Gates ใหม่
- หากแก้ร่างหลัง Human Review ต้องยกเลิกสถานะ `READY_FOR_SUBMISSION` และตรวจทานใหม่
- ห้ามลบสถานะเดิม ให้บันทึกเหตุผล ผู้ดำเนินการ เวลา และหลักฐานใน `auditTrail`

## 7. Error handling

ทุกการเปลี่ยนสถานะที่ไม่ผ่านต้องคืนผลแบบมีโครงสร้าง:

```yaml
TransitionResult:
  allowed: boolean
  fromState: string
  requestedState: string
  failedGates: string[]
  missingInformation: string[]
  requiredEvidence: string[]
  riskFlags: string[]
  nextSafeAction: string
```

ระบบต้องไม่ใช้ข้อความกว้าง ๆ เช่น “ไม่สามารถดำเนินการได้” โดยไม่ระบุสาเหตุและการดำเนินการถัดไป

## 8. Acceptance scenarios

1. **ข้อมูลไม่ครบแต่ค้นได้:** อนุญาตให้ไป `AUTHORITY_CHECK` ได้ แต่ยังไม่อนุญาต `DRAFT_ALLOWED`
2. **วัสดุ/ครุภัณฑ์ไม่ชัด:** คงสถานะ `CLASSIFICATION_PENDING` และเปิดรายการหลักฐานที่ต้องตรวจ
3. **กฎหมายต่างฉบับขัดกัน:** เปิด `decisionLock` และส่งกลับ `AUTHORITY_CHECK`
4. **ขอร่างรายงานขอซื้อก่อนอนุมัติหลักการ:** ไม่อนุญาตให้ข้ามขั้น เว้นแต่มีหลักฐานฐานอำนาจรองรับและผู้ตรวจทานยืนยัน
5. **แก้ไขวงเงินหลังผ่าน Quality Gate:** ย้อนกลับเพื่อประเมิน readiness และ quality ใหม่
6. **แก้ไขร่างหลัง Human Review:** ยกเลิกความพร้อมเสนอและบังคับตรวจทานซ้ำ
7. **พบแนวทาง e-GP ฉบับใหม่:** บังคับตรวจ version/effective date ก่อนดำเนินการต่อ

## 9. Human responsibility

สถานะ `READY_FOR_SUBMISSION` หมายถึงเอกสารผ่านเงื่อนไขการตรวจของระบบและการตรวจทานที่กำหนดเท่านั้น ไม่ใช่การอนุมัติแทนผู้มีอำนาจ และไม่ตัดทอนความรับผิดชอบของเจ้าหน้าที่ผู้จัดทำ ผู้ตรวจสอบ หรือผู้อนุมัติ
